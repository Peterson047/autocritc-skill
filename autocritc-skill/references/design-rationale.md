# Design Rationale

Why Autocritic Pro is designed the way it is, what alternatives were considered, and where the current approach has limitations.

## Why invisible review beats verbalized critique

The original Autocritic-Skill (which this is based on) required the agent to "verbalize potential flaws before acting." This sounds good in theory but fails in practice for three reasons:

1. **It doesn't improve output quality.** When an agent says "I notice this function doesn't handle null values — I'll add a check," it's performing critique as narrative. The critique and the fix happen in the same generation pass, so the "verbalization" is just a performance. The fix would have happened anyway (or not happened despite the verbalization).

2. **It wastes tokens and attention.** The user doesn't need to read the agent's internal deliberation. Every token spent on "Let me review my approach..." is a token not spent on the actual output or on maintaining context for the rest of the conversation.

3. **It creates a false sense of quality.** Seeing the agent critique itself makes users feel the output is more rigorous. But visible critique and actual quality are uncorrelated — the agent is just as likely to miss a flaw whether it verbalizes or not.

The invisible approach (generate → shift perspective → correct silently → deliver) addresses all three: the review actually happens (the perspective shift is a real cognitive operation, not a performance), it costs zero visible tokens, and the output quality speaks for itself.

The `[Refinement Note]` mechanism exists to give users confidence the review happened, without the verbosity of showing the full process.

## Why ambiguity routing beats "always ask" or "never ask"

### "Always ask" (the original approach)

The original skill stopped on every underspecified request. This was designed for Claude, where it works reasonably well — Claude's caution means it was already going to ask most of these questions anyway, and the skill just formalized the format.

But on Gemini, "always ask" is crippling. Gemini's proactivity is its biggest strength — it can execute a 3-step task in one shot. Forcing it to ask "Which library should I use for HTTP requests?" before writing a Python script is like putting training wheels on a professional cyclist.

On GPT-4, "always ask" produces a robotic, support-ticket interaction pattern. "To proceed with your request to create a login function, please clarify: 1) Which framework? 2) Which database? 3) Which authentication method?"

### "Never ask" (the opposite extreme)

On Claude, "never ask" is dangerous. Claude's caution is well-calibrated — when it wants to ask, it's usually because there's a genuine ambiguity that would produce wrong output. Suppressing that instinct leads to confident but incorrect results.

On Gemini, "never ask" works 90% of the time but fails catastrophically on the 10% where the task is genuinely impossible without user input. The agent charges forward with assumptions that produce completely wrong architectures.

### Adaptive routing (the current approach)

By defining HIGH ambiguity strictly as "missing information that makes delivery impossible or fundamentally wrong," we create a single rule that works differently on each model:

- Claude's high threshold for what it considers "impossible" means it asks less than its default but still asks when it truly needs to. The definition of HIGH is strict enough that Claude's over-asking is restrained.
- Gemini's low threshold for what it considers "executable" means it almost always takes the LOW/MEDIUM path, preserving its speed. The HIGH path exists as a safety net for the rare cases where even Gemini can't guess.
- GPT-4 follows the branching logic precisely, gaining a decision framework it didn't have before.

## Why prohibit fake testing instead of requiring real testing

We could have written "after generating code, run tests." The problem is that LLMs can't actually run code. When asked to "test," they do one of three things:

1. **Fake test blocks** — Write `assert` statements that "prove" the code works. But these assertions are generated by the same model that wrote the code, using the same reasoning, so they have the same blind spots.

2. **Execution simulation** — "If you run this with input X, the output will be Y." This is just the model tracing its own logic, which it already did during generation. It catches zero additional errors.

3. **Confident claims** — "I've verified this works correctly." This is pure theater.

All three are expensive in tokens, add no verification value, and create false confidence. The alternative — structural and logical review during the perspective shift — is actually more effective because it examines the code's architecture and logic paths rather than simulating a single happy-path execution.

When users actually want tests (they say "write tests for this"), the skill allows it because the tests become the deliverable, not verification.

## The perspective shift technique

This is the most important mechanism in the skill, and it's worth understanding why it works.

### The problem: autoregressive self-agreement

LLMs generate text one token at a time, where each token is conditioned on all previous tokens. This creates a coherence pressure — the model tends to agree with and extend what it has already said, even if the previous tokens contained an error. It's similar to how humans, when writing, tend to rationalize their earlier statements rather than contradicting them.

This means that if a model writes a function with a subtle bug at token 50, tokens 51-200 will tend to work around the bug, explain it, or simply not notice it — because contradicting the established text would reduce coherence.

### The solution: instruction-following as a reset

By instructing the model to "now read this as if you are a senior engineer reviewing a junior's PR," we leverage the model's instruction-following capability to create a context switch. The model is now in "reviewer mode" rather than "author mode." It's reading the text as a foreign artifact rather than its own creation.

This doesn't guarantee the model will find every flaw — it's not a perfect technique. But it significantly increases the chance of catching errors compared to the default autoregressive pass, because the reviewer persona has no investment in defending the original text.

### Limitations

- **Shorter outputs** are harder to critique because there's less surface area for flaws. A 5-line function might look fine at first glance even if it has a subtle bug.
- **The quality of the review varies by model** — models with stronger reasoning capabilities (Claude Opus, GPT-4) perform the perspective shift more effectively.
- **It's an instruction, not a guaranteed cognitive process.** Some models may perform the shift superficially, reading the text but not genuinely challenging it. The effectiveness depends on the model's training on instruction-following.

## Edge cases and known limitations

### The ambiguity boundary is subjective

Whether something counts as HIGH or LOW/MEDIUM ambiguity is inherently a judgment call. "Create an API" — is that HIGH (which framework? which database?) or LOW (REST is the default, use the project's existing stack)? The skill mitigates this by defining HIGH as "delivery is impossible or fundamentally wrong," which is a high bar. The autonomous assumption log in `decisions.md` creates a paper trail the user can audit.

### The skill doesn't make the model smarter

This is a behavioral skill, not a capability enhancer. It can't make a model catch errors it doesn't have the reasoning capacity to see. What it does is ensure the model uses its existing capacity more effectively — reviewing before delivering, asking when truly stuck, and not wasting tokens on theater.

### State file drift

If the agent crashes mid-session or the user manually edits state files, the state may become inconsistent. The files are designed to be human-readable and manually correctable as a trade-off for zero dependencies.

### Over-suppression of questions

There's a risk that the skill makes the agent too reluctant to ask, especially on Claude where the model is already being pushed away from its natural caution. If the user notices the agent making too many wrong assumptions, the fix is to add more specific context to the request rather than disabling the skill.
